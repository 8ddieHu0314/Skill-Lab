# v0.8.0: Trace Analysis & Scenario DSL

**Status:** Planned

## Overview

Ships two long-deferred features that finally expose the existing `evaluators/trace_evaluator.py` + `tracechecks/` infrastructure as first-class user surface:

1. **`sklab eval-trace`** — validate execution JSONL traces against YAML-defined checks (deferred from v0.2.0, hidden command to date).
2. **Given/When/Then scenario DSL** — `scenarios.yaml` as a structured alternative to the flat `triggers.yaml` format (deferred from v0.2.0 → v0.3.0 and never shipped).

Both pieces are natural extensions of v0.7.0's persistence layer (`.sklab/evals/`) and close the loop on the evaluation story: users can now define *what good execution looks like*, not just *whether the skill triggered*.

## Problem

Today, skill authors have two evaluation surfaces:
- **Static analysis** (`sklab evaluate`) — fast, deterministic, but can't see runtime behavior.
- **Trigger testing** (`sklab trigger`) — runs a live agent, but only records a binary "did it fire?" outcome.

What's missing: a way to assert on *what the agent actually did* during execution. Did it call the expected tools? Did it create the right files? Did it get stuck in a loop? The `tracechecks/` module with 5 handlers (`command_presence`, `file_creation`, `event_sequence`, `loop_detection`, `efficiency`) has quietly existed since v0.2.0 but has no user-facing CLI and no way to define checks in YAML.

Separately, the `triggers.yaml` format is flat — fine for "does this prompt trigger the skill?" but insufficient for multi-step scenarios where the interesting question is "given X, when the user says Y, then Z should happen." v0.2.0's spec promised a GWT DSL; it never shipped.

## Solution

### 1. `sklab eval-trace` (public)

Unhide the existing command, wire it into `commands/`, and give it first-class reporter support.

```bash
# Analyze a trace file against default check set
sklab eval-trace ./my-skill --trace ./execution.jsonl

# Analyze against custom YAML-defined checks
sklab eval-trace ./my-skill --trace ./execution.jsonl --checks .sklab/tests/trace_checks.yaml

# Pipe from sklab trigger for end-to-end eval
sklab trigger ./my-skill --save-traces .sklab/traces/
sklab eval-trace ./my-skill --trace .sklab/traces/latest.jsonl

# JSON output for CI
sklab eval-trace ./my-skill --trace trace.jsonl --format json
```

**YAML check definition** (`.sklab/tests/trace_checks.yaml`):

```yaml
skill: my-skill
checks:
  - type: command_presence
    name: "Must run pytest"
    required_commands: ["pytest"]
    severity: high

  - type: file_creation
    name: "Writes report to expected path"
    expected_files: ["reports/*.md"]
    severity: medium

  - type: event_sequence
    name: "Reads config before writing output"
    sequence: ["read:config.yaml", "write:output.json"]
    severity: medium

  - type: loop_detection
    name: "No runaway loops"
    max_repeated_events: 5
    severity: high

  - type: efficiency
    name: "Under 10 tool calls"
    max_tool_calls: 10
    severity: low
```

### 2. Scenario DSL (`scenarios.yaml`)

Add `.sklab/tests/scenarios.yaml` as a parallel format to `triggers.yaml`. `sklab trigger` auto-detects which file(s) are present and runs both if both exist.

```yaml
skill: my-skill
scenarios:
  - name: "Creates report when asked"
    given:
      - skill: my-skill
      - runtime: claude-cli
      - fixture_files: ["data/input.csv"]
    when:
      - prompt: "Generate the weekly report"
      - trigger_type: implicit
    then:
      - skill_triggered: true
      - files_created: ["reports/*.md"]
      - commands_run: ["pandas"]
      - exit_code: 0

  - name: "Refuses when data missing"
    given:
      - skill: my-skill
    when:
      - prompt: "Generate the weekly report"
    then:
      - skill_triggered: true
      - output_contains: "input file not found"
      - exit_code: 1
```

The `then:` block compiles to trace checks (mapped onto the existing `tracechecks/` handlers) plus the existing trigger-detection logic. This means **no new check handlers need to be written** — the DSL is a surface layer over v0.2.0 infrastructure.

### 3. `sklab generate` extension

`sklab generate` currently produces `triggers.yaml`. Add `--format scenarios` to generate the GWT form instead, plus `--format both` for side-by-side output. Uses the same LLM pipeline; swaps the prompt template.

├── commands/

## Non-Goals

- **New trace-check handlers** — the 5 existing handlers cover the common cases. New handlers can land in patches.
- **Cross-scenario state** — scenarios are independent runs; no shared fixtures across scenarios in this release.
- **Snapshot testing** — asserting on full trace equality is deferred; too brittle without a curated corpus.
- **Networked trace storage** — `.sklab/traces/` is local-only. Cloud sync belongs to a later release.

## Verification

```bash
# Trace analysis against existing handler set
sklab trigger ./my-skill --save-traces .sklab/traces/
sklab eval-trace ./my-skill --trace .sklab/traces/latest.jsonl

# Scenario DSL end-to-end
cat > .sklab/tests/scenarios.yaml <<EOF
skill: my-skill
scenarios:
  - name: "Smoke test"
    when: [{ prompt: "do the thing" }]
    then: [{ skill_triggered: true }]
EOF
sklab trigger ./my-skill   # Runs both triggers.yaml and scenarios.yaml

# LLM generation for both formats
sklab generate ./my-skill --format scenarios
sklab generate ./my-skill --format both
```

## Migration Notes

- No breaking changes. `triggers.yaml` continues to work; `scenarios.yaml` is additive.
- Skills that previously depended on the hidden `eval-trace` command (internal use only) will see no behavior change — only the visibility flag flips.
- `--save-traces` on `sklab trigger` is opt-in. Default behavior (traces discarded after analysis) is unchanged.
