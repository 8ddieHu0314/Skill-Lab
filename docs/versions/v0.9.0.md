# v0.9.0: API-Based Runtimes

**Status:** Planned

## Overview

Direct API runtimes where skill-lab handles the agent loop internally. Previously scoped for v0.8.0; pushed to v0.9.0 so v0.8.0 could ship the trace analysis + scenario DSL surface first.

## Problem

CLI-based runtimes require users to:
1. Install Codex CLI or Claude CLI separately
2. Configure authentication for those CLIs
3. Manage CLI versions

## Solution

Built-in API runtimes:
- User provides API key via environment variable
- skill-lab handles the agent loop internally
- Single install: `pip install skill-lab`

## CLI Commands

```bash
# Set API key
export OPENAI_API_KEY=sk-...
export ANTHROPIC_API_KEY=sk-ant-...

# Use API-based runtime
sklab trigger ./my-skill --runtime openai-api
sklab trigger ./my-skill --runtime anthropic-api

# Auto-detect: prefer API if key present, fallback to CLI
sklab trigger ./my-skill --runtime auto
```

## Architecture

```
src/skill_lab/
├── runtimes/
│   ├── openai_api_runtime.py    # OpenAI API + agent loop (thin adapter)
│   └── anthropic_api_runtime.py # Anthropic API + agent loop (thin adapter)
└── agent/
    ├── loop.py                  # Provider-agnostic agent loop (uses LLMProvider)
    └── tools.py                 # Tool execution (bash, read, write, edit)
```

## Agent Loop Implementation

```
1. Load skill SKILL.md into system prompt
2. Send user prompt to API
3. If API returns tool_use:
   a. Execute tool via ToolExecutor (sandboxed by ExecutionProvider)
   b. Send tool result back to API
   c. Repeat from step 3
4. Capture all events as TraceEvent (matching tracechecks/ format)
5. Return trace for analysis
```

## Integration with v0.8.0

v0.8.0 shipped `sklab eval-trace` and the scenario DSL. v0.9.0's API runtimes emit the same `TraceEvent` shape, so all v0.8.0 trace checks and scenario `then:` assertions work against API-runtime traces without modification. This ordering is deliberate: traces were standardized before we added more producers of them.

## Architecture Decisions

1. **Single provider-agnostic loop** — `agent/loop.py` takes an `LLMProvider` (already exists in `core/llm.py`) and a `ToolExecutor`. Runtime files are thin adapters that map Anthropic/OpenAI-specific tool schemas onto the shared loop. Avoids forking loop logic per provider.

2. **Tool name parity with Claude Code** — Use `Bash`, `Read`, `Edit`, `Write` so v0.8.0's trace checks (`command_presence`, `file_creation`) work without per-runtime translation.

3. **`ExecutionProvider` refactor** — Currently, `LocalProvider`/`DockerProvider` wrap *process spawning* (CLI runtimes). With API runtimes, skill-lab is the agent, so sandboxing now wraps *tool execution*. Refactor `ExecutionProvider` to expose a `ToolExecutor(provider)` primitive while keeping the CLI-runtime spawn path intact.

4. **Token accounting** — API runtimes return first-class token usage. Wire `GenerationUsage` (already in `core/llm.py`) into the trigger trace so `sklab stats` token totals become accurate for API runs.

5. **Dependency status** — `anthropic` and `openai` are already required dependencies (used by judge and optimizer). No `pyproject.toml` change needed.

## Risks / Open Questions

- **DockerProvider refactor blast radius** — if the sandboxing refactor proves messy, consider shipping API runtimes as local-only in v0.9.0 and deferring Docker-sandboxed API runtimes.
- **Multi-turn cost** — API runtimes burn user money per trigger test. At ~13 tests/skill, multi-turn is pricey. Ship `--max-turns` cap and a cost preview prompt.
- **CLI vs API trace divergence** — even with matching tool names, CLI runtimes capture stderr/exit codes the API path can't see. Document which trace checks are runtime-sensitive.
- **Scope width** — this release bundles API runtimes *plus* ~5 v0.7.0 deferrals. Consider splitting off the v0.7.0 deferrals into v0.9.1 if timeline tightens.
